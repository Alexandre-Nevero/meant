# ADR-0080 — The judge's production config is provisional, and shares no rate limit with the coach

- **Date:** 2026-09-22
- **Status:** Accepted
- **Context:** ADR-0073 permits building the judge and writing `judgment` rows before a real, non-synthetic eval exists — only rendering a verdict to the user is gated. The judge spike's own findings (`docs/superpowers/specs/2026-09-21-judge-spike-findings.md`) measured the four-label taxonomy against `openai/gpt-oss-120b` as the clear winner on every metric, but on a synthetic, self-labelled corpus — the findings document's own words are that this "does not license shipping the judge against real users on this evidence alone." Separately, the real coach (ADR-0079) already uses `openai/gpt-oss-120b`, described there as "the larger tier over the judge's cheaper default" — an assumption made about a judge that did not exist yet, not a decision anyone took. Building the judge on the same model the coach uses would silently make them share `DAILY_COACH_TURNS`' rate-limit query, since both would write `inference_call` rows with `model = 'openai/gpt-oss-120b'` for the same user — the coach's own final review (PR #72) flagged this as a known, then-hypothetical hazard (issue #70).
- **Decision:** **The judge uses the four-label taxonomy and `openai/gpt-oss-120b`, matching the spike's measured (if synthetic) winner** — not the cheaper tier ADR-0079 assumed, because the evidence, thin as it is, points the other way, and using a worse model to avoid a solvable naming collision would be the wrong trade. **The collision is resolved structurally, not by model choice:** every judge analysis writes a real, non-empty `session_ids` array to `inference_call` (one call always covers at least one session); every coach turn writes `session_ids = '{}'` (ADR-0079, a turn covers no batch of sessions). Both `DAILY_ANALYSIS_CAP` and `DAILY_COACH_TURNS` add `and session_ids = '{}'` (coach) or `and session_ids <> '{}'` (judge) to their existing `user_id`/`model`/`at` predicate, so the two features can never consume each other's budget regardless of which models they use, now or later.

  **The confidence floor is provisional, not measured.** The judge-spike findings suggested a floor around 0.70 "looks like a reasonable candidate" on synthetic data, explicitly warning not to trust the specific number. `PROVISIONAL_MIN_CONFIDENCE = 0.70` (`lib/thresholds.ts`) is that placeholder: below it, the API labels a visit `unknown` in its response; at or above it, the real model label passes through. The stored `judgment.label`/`judgment.confidence` are always the model's raw output, unfiltered — the floor is applied only when *presenting* a result, so re-deriving the real floor later never requires re-running the model. (Named to avoid the literal substring `CONFIDENCE_FLOOR`, which `test/companion-state.test.js` asserts never reappears in `thresholds.ts` — that string names ADR-0057's deleted live-signal threshold, unrelated to this one.)
- **Consequences:** `judgment` rows accumulate under a config that may be wrong once real evidence exists — that is accepted (ADR-0073 already accepted it for the mechanism as a whole). Re-tuning the floor or the model later is a config change, not a migration, since nothing about storage depends on either value. `app/api/coach/chat/route.ts`'s comment calling `openai/gpt-oss-120b` "the judge's cheaper default" is now stale and is corrected in the same commit as this ADR (ADR-0063: reconcile stale documents, don't silently pick one).
- **Source:** owner decision 2026-09-22; ADR-0072, ADR-0073, ADR-0078, ADR-0079; the judge spike findings.
